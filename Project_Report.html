ABLE: Technical Project Report

Project Name: ABLE (Awareness, Accessibility, Inclusion)
Domain: Accessibility Tech & Social Welfare
Architecture: Client-Server Web Application

Executive Summary: ABLE is a full-stack web application designed to bridge the gap between citizens with mobility or accessibility needs and verified volunteers. It serves as both a rapid response system for requesting physical assistance and a city-wide tracker for reporting infrastructure barriers.

1. System Architecture

  • Frontend (Client): Built with pure HTML5, CSS3, and Vanilla Javascript. It uses asynchronous HTTP requests (fetch) to communicate with the backend. It also utilizes Leaflet.js for rendering interactive maps.
  • Backend (Server): Built using Python and the Flask micro-framework. It exposes RESTful API endpoints that the frontend consumes.
  • Database: Uses SQLite3, a lightweight file-based relational database (database.db), for secure data persistence.

2. Database Schema (app.py)

The backend initializes five primary SQL tables:

  • users: Stores authenticated users (Admin, Volunteer, Citizen) with their emails, passwords, and access roles.
  • requests: Stores assistance requests (location, type of help needed) and tracks their status (Pending, Dispatched, Resolved).
  • reports: Stores physical barrier reports (broken ramps, blocked paths) along with their severity level.
  • pending_volunteers: A staging table for new volunteers who have registered but have not yet had their IDs verified by an Admin.
  • directory: A database of verified accessible locations (e.g., malls with wheelchair ramps).

3. Backend API Endpoints (Flask)

The Python server manages data flow through these primary routes:

  • /api/login (POST): Authenticates users against the users table and returns their assigned role, determining which dashboard they see.
  • /api/requests (GET / POST): Fetches all active requests, or allows a citizen to insert a new request into the database.
  • /api/reports (GET / POST): Fetches all barrier reports, or allows a citizen to log a new infrastructure issue.
  • /api/requests/<id>/accept (POST): Triggered when a Volunteer clicks "Accept Job". It updates the database status of the request from Pending to Dispatched.
  • /api/volunteers (GET / POST): Used for the Volunteer Registration form. Submits the user's details and ID to the pending_volunteers table.
  • /api/approve_volunteer (POST): Admin-only route. Deletes the applicant from pending_volunteers and securely inserts them into the users table, granting them login access.

4. Frontend Javascript Logic (script.js)

The script.js file acts as the brain of the frontend UI:

  • Authentication State (localStorage): When a user logs in, the JS stores able_logged_in and able_role in the browser's local storage. This determines which navigation bar to securely inject into the DOM.
  • Dynamic Data Fetching (loadDynamicData): When a dashboard loads, this function asynchronously requests data from the backend APIs and dynamically generates the HTML <tr> rows for the tables. It includes logic to filter history tables based on the logged-in user.
  • Interactive Map (initVolunteerMap): Initializes a Leaflet.js map centered on Pune. It loops through the live Pending requests from the database, generates geographical coordinates, and drops interactive red alert markers on the map.
  • Accessibility Engine: Handles the high-contrast Dark Mode toggle, text enlargement, and live English-to-Marathi DOM translation by sweeping through HTML elements and replacing text strings.

5. User Roles & Workflows

A. The Citizen Workflow

  1. A citizen logs in and navigates to New Request.
  2. They submit a request for a "Wheelchair Escort" at a specific location.
  3. The frontend POSTs this to /api/requests, saving it to SQLite with a Pending status.
  4. The citizen tracks the real-time status on their "Active Requests" dashboard.

B. The Volunteer Workflow

  1. A new student fills out the registration form and uploads their College ID.
  2. They are placed in the pending_volunteers queue.
  3. Once approved by an Admin, they can log into the Volunteer Dashboard.
  4. They open the Nearby Requests map, see the citizen's red marker, and click "Accept". The backend marks the job as Dispatched.
  5. Upon completing enough hours, they can download an automated PDF Certificate of Appreciation.

C. The Admin Workflow

  1. The Admin acts as the ultimate system moderator.
  2. They review the Pending Verifications table. Clicking "View ID" pulls up the uploaded ID card. If valid, they click "Approve", which triggers /api/approve_volunteer to officially create the account.
  3. They monitor the total volume of barrier reports and dispatch metrics across the city through dynamically updating tables.
